# Data card

Provenance, schema, statistics and known biases of the data FraudLens trains on.

---

## 1. Which dataset

The project supports two sources, sharing an identical schema so anything built
against one runs unchanged on the other.

| Source | Command | Status |
|---|---|---|
| **Synthetic** (default) | `python scripts/prepare_data.py` | **What the shipped model was trained on** |
| Sparkov (Kaggle) | `python scripts/prepare_data.py --source kaggle` | Supported, not yet used |

> ### ⚠️ The shipped model is trained on synthetic data
>
> Every result in the README and [`MODEL_CARD.md`](MODEL_CARD.md) comes from
> generated data. The generator is realistic in *structure* but easier than
> reality. These figures are **not a benchmark result** and are not comparable
> to published work on real datasets.
>
> The methodology is the transferable part. Real data drops in via one flag, and
> the numbers will fall.

### Why synthetic at all

Three reasons, in order of weight:

1. **Ground truth about mechanism.** Real labels say *that* a transaction was
   fraud, never *why*. Here every fraudulent row is tagged with the typology
   that produced it, so detection is measurable **per attack pattern** — which
   is how a fraud team actually reasons about coverage. That per-typology table
   is the most informative result in the project and no public dataset supports it.
2. **No credentials on the critical path.** A fresh clone and CI both run with
   no Kaggle token and no 400 MB download.
3. **A controllable difficulty floor.** See §5.

## 2. Real-source provenance

[Credit Card Transactions Fraud Detection Dataset](https://www.kaggle.com/datasets/kartik2112/fraud-detection)
— 1,852,394 transactions, 1,000 customers, 800 merchants, 2019-01-01 to
2020-12-31, generated by Brandon Harris's Sparkov simulator.

Chosen over the more common PCA-anonymised alternatives (the ULB
`creditcard.csv`) because every column is semantically meaningful. With `V1–V28`
principal components, "behavioural analysis" and "explainable AI" become hollow:
SHAP reporting *"V14 was low"* means nothing to an analyst. Customer **and**
merchant coordinates also make genuine geo-velocity features possible.

**Licence.** CC0 / public domain on Kaggle. Simulated, so no real customer data
and no PII exposure. Requires a free Kaggle account to download.

## 3. Schema

23 raw columns; 19 survive ingestion.

| Column | Type | Notes |
|---|---|---|
| `trans_date_trans_time` | datetime | Ordering key for every temporal operation |
| `cc_num` | int64 | Card identifier; all features group by this |
| `merchant` | string | Unique merchant identity |
| `category` | string | 14 merchant categories |
| `amt` | float | Transaction value |
| `gender` | string | `M` / `F` |
| `city`, `state`, `zip` | string/int | Customer location |
| `lat`, `long` | float | Customer **home** coordinates |
| `city_pop` | int | Population of customer's city |
| `job` | string | Customer occupation |
| `dob` | datetime | Date of birth → `age_years` |
| `trans_num` | string | Unique transaction id |
| `unix_time` | int64 | Redundant with the timestamp |
| `merch_lat`, `merch_long` | float | **Merchant** coordinates |
| `is_fraud` | int | Target, 0/1 |
| `fraud_typology` | string | **Synthetic only.** Never a model input |

### Dropped at ingestion

`first`, `last`, `street` — effectively unique per customer. Retaining them
would let the model memorise individuals rather than learn behaviour: a leakage
risk and a privacy problem. Enforced in `loader.py`, asserted by test.

### Type handling worth noting

`cc_num` is read as **explicit int64**. Inferred as float64, a 16-digit card
number exceeds float64 integer precision and distinct cards would silently
collide — corrupting every card-grouped feature with no error raised.

**Fraudulent transactions have a *lower* median than legitimate ones.** Card

## 5. Fraud typologies (synthetic only)

| Typology | Rows | Share | Pattern |
|---|---:|---:|---|
| `card_testing` | 1,690 | 44.1% | Small amounts, many merchants, minutes apart |
| `spending_spree` | 808 | 21.1% | Escalating purchases before the card is reported |
| **`subtle`** | **691** | **18.0%** | **Deliberately unremarkable — undetectable** |
| `account_takeover` | 531 | 13.8% | High value, unfamiliar merchant, overnight |
| `geo_impossible` | 116 | 3.0% | Cloned card used impossibly far away |

### The `subtle` typology is the point

18% of fraud is generated to be statistically indistinguishable from ordinary
spending: familiar merchant, normal amount, mid-afternoon, no velocity anomaly.

Without it, every fraudulent transaction carries at least one loud signal, recall
approaches 1.0, and the metrics describe the generator rather than the model. It
sets an **irreducible difficulty floor** — which is also true in production,
where some fraud simply cannot be caught from transaction features alone.

Measured recall on it is **0.000**, exactly as intended.

## 6. Generator design decisions

Two choices are load-bearing; both were fixes to measured defects.

**Cities, not uniform scatter.** Merchants and customers cluster into 40 city
centres. An earlier version scattered merchants uniformly across a continent,
and two consecutive *legitimate* purchases landed ~991 km apart — flagging **14%
of genuine transactions as impossible travel**. Clustering dropped that to
**1.0%** while fraud retained 78%. Locality is what makes geo features signal
rather than noise.

**Trips are windows, not points.** A traveller flies somewhere, spends several
days, flies back. Scattering isolated distant transactions would manufacture
impossible travel on legitimate cards.

## 7. Known biases and limitations

1. **Synthetic** — the dominant caveat. §1.
2. **US-shaped.** Coordinates, state codes and city populations follow a US
   distribution. Nothing has been validated on UK or EU patterns.
3. **Only 400 cards.** Real portfolios have millions. Per-card behaviour is
   better-sampled here than reality would allow, which likely flatters the
   behavioural features.
4. **Fraud rate is a design parameter**, set to 0.58%. Real rates vary by orders
   of magnitude across channel and geography.
5. **No merchant-side view.** Card-centric only, so merchant collusion is
   invisible.
6. **Demographics are inputs.** `gender`, `age_years` and `city_pop` reach the
   model. **No disparate-impact analysis has been performed** — see
   [`MODEL_CARD.md`](MODEL_CARD.md) §7 item 8, which is a deployment blocker.
7. **Labels are perfect.** Every fraud is labelled, immediately and correctly.
   Real labels arrive weeks late via chargebacks, are incomplete, and contain
   mistakes. This is a significant and unmodelled simplification.

## 8. The committed sample

`data/sample/transactions_sample.csv` — **5,000 rows, 29 fraud (0.58%)**,
spanning the full date range.

Drawn with `stratified_time_sample`, which samples each class independently and
preserves chronological order. A naive `df.sample(5000)` on a 0.58%-positive
dataset yields a handful of frauds and a rate that swings wildly with the seed,
making any test asserting on class balance flaky.

This is the **only** data in version control. It exists so tests and CI run
without credentials or a large download. Raw and processed data are git-ignored.

## 9. Reproduction

```bash
python scripts/prepare_data.py --customers 400 --merchants 600 --seed 42
```

Deterministic given the seed. Defaults reproduce the statistics above exactly.
